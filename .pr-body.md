## What

One CMake flag separates a green build from a wall of `fatal error C1189` when building the CUDA targets on Windows: CUDA 13's CCCL headers refuse cl.exe's traditional preprocessor. The fix follows the route the `CMakeLists.txt` already uses for `/Zc:__cplusplus` one line above — hand the option to nvcc's host compiler via `-Xcompiler`:

```cmake
if(CMAKE_CXX_COMPILER_ID STREQUAL "MSVC")
  ...
  string(APPEND CMAKE_CUDA_FLAGS " -Xcompiler=/Zc:preprocessor")
endif()
```

## Why CI doesn't see it

The Windows CI jobs compile and test the CPU path only; the CUDA targets are never built with MSVC there. This is a Windows + CUDA (Blackwell `sm_120`) build, where every `.cu` translation unit that reaches CCCL dies in `cccl/cuda/std/__cccl/preprocessor.h(23)`.

## Proof (controlled A/B on this branch)

- Worktree at `c5f9fa24` **without** this commit, building only `dec_gdn_rec.cu.obj`: FAILED, `fatal error C1189: MSVC/cl.exe with traditional preprocessor is used. Please switch to the standard conforming preprocessor by passing /Zc:preprocessor to cl.exe` — the header prescribes exactly this flag.
- Same sources **with** the commit: clean-room Release build green (194/194 targets), incremental re-verification on top of `c5f9fa24` green (77/77 including the rebuilt `mid_chain.cu`), `ctest -L cpu` 34/34 (excluded `expert_multi_test`, which requires AVX-512 the host CPU doesn't have — a host limitation, not a regression).
- Runtime: `basalt.exe serve` loads a pack and runs 262K-context chat and tool-call agent sessions on an RTX 5070 Ti (Windows 11, Ryzen 5800X3D, 128 GB) with no fallbacks in the log. Numbers are agent development runs only, per AGENTS.md.

CCCL also offers `CCCL_IGNORE_MSVC_TRADITIONAL_PREPROCESSOR_WARNING` to silence the diagnostic, but switching the preprocessor is the actual fix, so that's what this does.

The `[[noreturn]]`-ordering MSVC issue we also hit while bringing the tree up was fixed upstream in `63b40f2d` before this branch, so only the flag remains.
